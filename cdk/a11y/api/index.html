Hooks

useFocusOrigin: (options?: UseFocusOriginOptions) => Signal<FocusOrigin>

Lazy, per-component replacement for useFocusMonitor() (which — as of this writing — wires up via useVisibleTask$, forcing its JS to load and run eagerly on every resumed instance regardless of whether the user ever interacts with it). useFocusOrigin() instead calls useOn(), which only attaches a serialized on:<event> reference to the current component's host element at SSR/render time; the handler's chunk is downloaded and run by qwikloader the FIRST time the event actually fires — never before.

Details

Call from inside a component$ body (before the return), same as any other use* hook; it attaches to whichever element that component renders as its root. Returns a Signal<FocusOrigin> the caller can read declaratively (e.g. to compute cdk-focused / cdk-keyboard-focused / cdk-mouse-focused / cdk-touch-focused / cdk-program-focused classes) — deliberately NOT a plain {value} shim like createFocusMonitor()'s return, because a plain mutation wouldn't trigger a re-render, and a real Qwik signal is also what survives Qwik's class prop replacing className wholesale on every unrelated re-render (see qwik-material/button-toggle/mat-button-toggle.tsx for why that matters). Origin resolution, simplified from InputModalityDetector + FocusMonitor's joint algorithm down to: - focusin (bubbles, unlike focus — covers descendant focus for free, i.e. upstream's checkChildren: true) resolves the origin: wasRecentKeydown() true means 'keyboard'; otherwise getRecentPointerModality() (./recent-keydown.ts — both eagerly, synchronously tracked at <QwikCdkRoot>, NOT via this component's own lazy pointerdown listener; see that file's doc comment for why a v2-only race demanded that for the pointer-modality flag too, not just the keydown one originally); otherwise 'program'. - focusout (bubbles version of blur) clears the origin. No checkChildren-style "don't clear if focus moved to a descendant" guard — callers with more than one focusable descendant under the host should reconsider; today's only caller (MatButtonToggle) has exactly one. - A pending origin written by focusVia() (see above) on the target element takes priority over both, exactly once, then is cleared — needed by callers (MatAccordion, MatExpansionPanelHeader) that must force 'program' even though a real keydown/click triggered the resulting focus. An earlier version of this hook used the browser's own :focus-visible pseudo-class instead of tracking real keydowns at all. That's simpler and race-free, but confirmed live to disagree with upstream's own algorithm for a bare SCRIPTED element.focus() call with no real keydown/mousedown behind it (e.g. Playwright's locator.focus()): Chromium's native heuristic matches :focus-visible there too, conflating "scripted, no recent interaction" with "real keyboard navigation", where upstream's FocusMonitor.getFocusOrigin() correctly falls through to 'program' (see qwik-material/tooltip's message-change scenario). Tracking real keydowns fixes that — but ONLY with a truly eager, always-installed listener; see recent-keydown.ts's doc comment for the two lazy attempts (useOn, then useOnDocument) that each lost the race against a REAL Tab press's own synchronous default action for a plain reason: neither one is guaranteed to be loaded+running before the very first keydown on the page, which <QwikCdkRoot>-level eager installation is.

focusVia(element: HTMLElement, origin: FocusOrigin, options?: FocusOptions) => void

Qwik-native replacement for upstream FocusMonitor.focusVia(element, origin, options): forces the ORIGIN of the very next focus event on element to origin, bypassing useFocusOrigin()'s normal pointerdown/:focus-visible heuristic entirely, then focuses it. Needed wherever upstream calls the real focusVia() with an origin the heuristic would get wrong — e.g. MatAccordion's FocusKeyManager-driven arrow-key navigation, whose origin is always 'program' even though a real keydown triggered it (CDK's FocusKeyManager never calls setFocusOrigin('keyboard')), and MatExpansionPanelHeader regaining focus as 'program' when its panel closes while focus was inside it.

Details

Only meaningful for elements that ALSO call useFocusOrigin() on themselves — plain element.focus() on an unrelated element is a no-op attribute write. Mirrors one more subtlety of the real FocusMonitor.focusVia(): if element is ALREADY the focused element (e.g. pressing End while already on the last header — FocusKeyManager.setActiveItem always calls .focus(origin) on the resulting active item, even when it's unchanged), calling .focus() again fires no new focus/focusin event in any browser, so the pending-origin attribute would never be read back off — it would just sit there, stuck, forever. Upstream's real engine special-cases this by updating the focus classes directly instead of relying on a focus event; this port dispatches a synthetic focusin instead, so the SAME useFocusOrigin() listener (and its pending-origin-attribute check) handles both paths uniformly.

resolveTreeKeydown(activeKey: string, eventKey: string, entries: readonly TreeKeyManagerItem<T>[], isExpanded: (key: string) => boolean, options: ResolveTreeKeydownOptions) => TreeKeydownAction<T>

Decides what a keydown on the currently-active tree item should do, given the full list of currently reachable (expansion-aware flattened) items.

Details

Faithful port of TreeKeyManager.onKeydown's switch + its _focusNextItem/_focusPreviousItem/_focusFirstItem/_focusLastItem/ _expandCurrentItem/_collapseCurrentItem/ _expandAllItemsAtCurrentItemLevel helpers, minus typeahead (see header comment). Returns {type: 'none'} for Tab, an unhandled key, or when activeKey isn't found in entries — the caller should NOT call event.preventDefault() in that case (matches upstream returning early without it).

AriaLivePoliteness

Qwik port of @angular/cdk/a11y's LiveAnnouncer (src/cdk/a11y/live-announcer/live-announcer.ts).

Details

Deviations from upstream: - No Angular DI / @Service() — a plain factory. Consumers (e.g. qwik-material/snack-bar's useMatSnackBar()) create and cache one themselves, the same pattern as every other qwik-cdk engine (createFocusTrap, createOverlayKeyboardDispatcher, ...). - The live element is created LAZILY, on the first announce() call, rather than eagerly when the service is constructed/injected. Upstream's LiveAnnouncer creates its <div class="cdk-live-announcer-element"> element in document.body the moment inject(LiveAnnouncer) runs (Angular DI has no lazy-construction story). Qwik has no eager construction moment that doesn't also mean "ship + run JS for every page that merely imports this module" (remediation rule 7 — lazy interaction plumbing); deferring to first real use means a page that never calls announce() never pays for the DOM node or its JS. Once created, the element is identical to upstream's (same classes/attrs), just later. - LiveAnnouncerMessage (string | SafeHtml) narrowed to string — no Angular DomSanitizer / SafeHtml concept in Qwik. - CdkAriaLive directive (the [cdkAriaLive] attribute directive) is not ported — out of scope for the snack-bar port that motivated this file. Possible politeness levels, mirroring upstream AriaLivePoliteness.

'off' | 'polite' | 'assertive'

TreeKeyManagerItem

Qwik port of src/cdk/a11y/key-manager/tree-key-manager.ts's decision algorithm (TreeKeyManager.onKeydown and its private helpers).

Details

Deviations from upstream: - A pure function (resolveTreeKeydown), not a stateful class. Upstream's TreeKeyManager is a long-lived object wrapping a QueryList/ Observable of TreeKeyManagerItems (each with imperative .focus()/ .expand()/etc. methods) and an RxJS change Subject. This port's only consumer (qwik-material/tree's MatTree) already recomputes its full flattened node list as a plain array on every render (see qwik-cdk/tree/flatten-tree.ts) and owns its own reactive state (expanded store, activeKey signal) directly — there is no "subscribe to items changing" concern (Qwik's own re-render IS that subscription) and no need for an object to hold item-list state between calls. resolveTreeKeydown takes the CURRENT flattened list + active key + pressed key and returns a plain description of what should happen; the caller applies it to its own store/signal. This keeps the algorithm itself (the genuinely-interesting, genuinely-unit-testable part — see tree-key-manager.spec.ts) completely free of Qwik/DOM concerns. - No typeahead support. Upstream's TreeKeyManager optionally wires a Typeahead (letter-key search) — no angular-parity.spec.ts scenario for mat-tree exercises it, and adding it would require this function to become stateful (a debounce buffer) for zero covered behavior. qwik-cdk/a11y/key-manager/typeahead.ts exists and could be wired in by a future caller that needs it; resolveTreeKeydown simply returns {type: 'none'} for an unrecognized key (including any letter), the same "not handled, don't preventDefault" outcome upstream's default: branch produces before it hands off to its typeahead instance. - shouldActivationFollowFocus not ported — no scenario uses it (CDK's own option for having every focus move also activate the item). - Initial-focus selection (upstream's _initializeFocus/makeFocusable, "focus the first non-skipped item without moving real browser focus") is NOT part of this function — it's a one-time computation the caller does directly from its already-flattened, already-filtered node list (list.find(e => !e.isDisabled)), since Qwik's SSR has no notion of "live items changed over time" to react to. Minimal per-node shape this algorithm needs — structurally satisfied by qwik-cdk/tree's FlatTreeEntry<T> without either package importing the other (mirrors upstream's own module boundary: TreeKeyManager lives in @angular/cdk/a11y, CdkTree lives in @angular/cdk/tree and imports IT, never the reverse).

UseFocusOriginOptions
NameTypeDescription
hostClasses?booleanAlso toggle the cdk-*-focused classes on the host element with classList, exactly as upstream FocusMonitor does, instead of leaving the caller to render them from the signal. A caller that renders its own class from the signal re-renders on every focus change, and Qwik rewrites the WHOLE class attribute on that re-render (the first one after resume diffs against the live DOM) — undoing any class another script toggled on the host meanwhile, which upstream preserves. With this set, the caller reads the signal untracked when computing its own class (so a re-render for another reason keeps the classes) and focus changes never re-render it.
