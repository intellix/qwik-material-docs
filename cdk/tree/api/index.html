Functions

collectInitialExpanded(roots: readonly CdkTreeNodeInput<T>[]) => Record<string, boolean>

Seeds the initial {key: expanded} map from every node's isExpanded input, read once at construction time (mirrors CdkTreeNode.isExpanded setter being driven by the [isExpanded] binding on first render).

flattenTree(roots: readonly CdkTreeNodeInput<T>[], isExpanded: (key: string) => boolean) => FlattenTreeResult<T>

Faithful port of CdkTree._flattenNestedNodesWithExpansion (the recursive walk that computes level/parent/aria-set bookkeeping for every node and filters the RETURNED list by ancestor expansion), generalized to also keep every node (all) for nested rendering.

focusTreeNodeAtIndex(treeRoot: Element, index: number) => void

Moves real DOM focus to the index-th rendered role="treeitem" element within treeRoot, in document order. Used by qwik-material/ tree's MatTree for keyboard-navigation focus moves (ArrowUp/Down/ Left/Right/Home/End) — these must move REAL focus, not just flip a tabindex attribute, since a scenario's later steps dispatch subsequent key presses to whatever element the browser currently considers focused.

Details

Deliberately index-based rather than a [data-*] attribute-value lookup: this port renders NO element identifying attribute beyond upstream's own real contract (role, aria-*, classes) — adding one would itself be a DOM-parity diff against the Angular reference (no such attribute exists there). The caller is responsible for computing index as this key's position within the SAME ordering treeRoot's children are rendered in — for the 'flat' variant, that's the ancestor-expansion-filtered visible list (DOM order matches exactly, one role="treeitem" per visible node); for 'nested', that's the UNFILTERED all list (every node is always in the DOM, in the same recursive pre-order querySelectorAll returns them in).

initialActiveKey(visible: readonly FlatTreeEntry<T>[]) => string | null

The first non-disabled entry in document order — the initial roving- tabindex target (mirrors TreeKeyManager._initializeFocus's makeFocusable() call, minus moving real browser focus, which SSR can't do and upstream itself deliberately avoids for the SAME reason — "the user isn't interacting with it").

Types

CdkTreeNodeInput

One node of a tree, as the consumer provides it. This is the node- definition shape this port settles on (see SYNC.md "Why nodes are data, not slotted templates" for the full rationale) — a recursive, SSR-readable, migration-friendly replacement for upstream's *matTreeNodeDef/childrenAccessor combination:

Details

- Hierarchy is a plain recursive children array, not a childrenAccessor function — Qwik component props must be serializable, and a function can't be (see qwik-material/table/SYNC.md's "a component$'s render function cannot be async" finding, which rules out calling a consumer function synchronously during render too, for the same reason MatTable ended up with pre-realized data instead of callbacks). Since the dev-app scenarios' own childrenAccessor = node => node.children ?? [] is already this shape, migrating a real childrenAccessor-based tree means calling it once, up front, to build this recursive array — trivial. - isExpandable/isDisabled/isExpanded are explicit flags (never inferred from children.length or a when predicate), mirroring upstream's OWN isExpandable input, which is likewise never inferred (see the scenario file's header comment) — carrying that explicitness straight into the port's API keeps a migration mechanical. - content is the node's pre-built inner JSX (what upstream's *matTreeNodeDef template would have rendered) — exactly MatColumnDef.header's shape, generalized to tree nodes. The ONE piece of content that needs LIVE access to the tree's own internal state — the toggle button's label/expanded-ness — is NOT baked into content as a static value; instead the consumer places a <CdkTreeNodeToggle> (cdk-tree-node-toggle.tsx) inside content, which reads the tree's shared state via context and re-renders itself independently, mirroring how MatSortHeader reads MAT_SORT_STATE from inside a MatColumnDef.header value in qwik-material/table.

CdkTreeToggleState

Shared state a tree (MatTree) provides and CdkTreeNodeToggle (placed anywhere inside a node's content, however deep) reads/writes. expanded/activeKey are Qwik reactive primitives (a useStore proxy and a useSignal), not plain values or closures — passing a signal/store through context for a descendant to mutate is a standard, fully serializable Qwik pattern (unlike a plain callback FUNCTION, which is NOT serializable — see qwik-cdk/tree/SYNC.md's design notes for why that distinction shaped this whole port). onExpandedChange/dataByKey are, respectively, a QRL (itself always serializable, regardless of where it's stashed) and a plain Map of DATA ONLY (no JSXOutput, unlike the FlatTreeEntrys it's built from) — both safe for the same reason.
