Autocomplete

Suggests options as the user types into a text input.

OverviewAPIExamples

MatAutocomplete : Component<MatAutocompleteProps>
NameTypeDescription
optionsSignal<ReadonlyArray<MatAutocompleteEntryDef>>Plain-data option/group definitions — see the module doc comment. DELIBERATELY reactive (unlike qwik-material/select's options) — the consumer writes a freshly-filtered array into this SIGNAL on every keystroke.
Details

**Must be the Signal itself** (options={filteredFruits}), never .value (options={filteredFruits.value}) — a hard requirement this port's select/chips/form-field ports didn't have, because none of them need MatFormField's control prop to carry genuinely LIVE data. MatFormField reads its own control prop EXACTLY ONCE (controlSnapshot = useSignal(() => props.control) in mat-form-field.tsx — confirmed by its own doc comment: freezing the REFERENCE, not just the nested prop values, is a deliberate fix for a real Qwik 1.20 core crash) — so a plain array value nested inside <MatFormField control={<MatAutocomplete options={...} />}> is captured once, at first render, and NEVER updates again, no matter how many times the consumer's own route re-renders with a fresh filtered array. A Signal sidesteps this the same way select-runtime.ts's value/activeIndex signals already do for MatSelectPanel: the SIGNAL OBJECT reference is what gets frozen into the snapshot, but that object is still the exact same live, mutable signal the consumer keeps writing to — reading .value off it (in render, in the useTask$ below, and in every $() handler) always sees the CURRENT value, unaffected by the outer props snapshot being stale. See autocomplete-option-resolver.ts's doc comment for the complementary "why re-resolving on every read is safe" half of this design.

Hooks

useMatAutocompleteProvider: (providerConfig?: MatAutocompleteProviderConfig) => void

Provides {@link MAT_AUTOCOMPLETE_CONFIG} and {@link MAT_AUTOCOMPLETE_SCROLL_STRATEGY} for this subtree — call once near the root (or anywhere deeper, to override just that part of the tree) so every MatAutocomplete descendant resolves its defaults/scroll strategy from providerConfig instead of the hardcoded fallbacks. Only these two contexts are provided; every other qwik-material configuration context stays whatever an ancestor (or nothing) already provided.

useMatAutocompleteStyles: () => void

Registers this entry point's CSS — scss/autocomplete/autocomplete-prebuilt.scss, compiled inside @layer qwik-material — for the rendering document, once: upstream's MatAutocomplete's styleUrl: 'autocomplete.css' (autocomplete.ts) (src/material/autocomplete/), attached when the component is first created, unscoped (ViewEncapsulation.None). Server rendering writes it before the first instance; a component first rendered in the browser brings it with its own chunk. Call it as the component's FIRST hook — Qwik keys a useStyles$ <style> by the call site AND the hook's index in the component, so only first-hook calls share one <style> (README "Component styles"). Exported for markup rendered without the component (a hand-written host, a plain render function).

Functions

resolveAutocompleteOptions(options: ReadonlyArray<MatAutocompleteEntryDef> | undefined, idCache: Map<string, string>, idGen: AutocompleteIdGenerator) => ResolvedAutocompleteOptions

Walks options (document order), flattening every option — direct or nested inside a group — into {@link ResolvedAutocompleteOptions}. Intended to be called FRESH on every render — see the module doc comment for why this is cheap and id-stable despite that.
