formatDateForDisplay(value: D | null) => string

Formats value for display using the hardcoded en-US DEFAULT_DATE_ADAPTER/ MAT_NATIVE_DATE_FORMATS singleton — exported so mat-datepicker-input.tsx/the consumer's dev-app route can compute the SSR-correct INITIAL value snapshot (mirrors MatInput's/ MatTimepickerInput's own initialValue/formatTimeForDisplay pattern) before any app-supplied adapter has been resolved (resolving a QRL factory is async — see resolveDateAdapterForPicker() below — but every initial render must be synchronous). handleDatepickerBlur(picker: MatDatepickerHandle<D>) => Promise<void>

Mirrors MatDatepickerInputBase._onBlur() — reformats a valid value with whichever DateAdapter/MatDateFormats this picker was configured with. See {@link handleDatepickerInput}'s doc comment for the resume-safety rationale.

Details

Re-parses the NATIVE INPUT's own current text first (via the same {@link parseAndCommitTypedDate} input uses), rather than trusting picker.value.value to already reflect it. This is NOT redundant: upstream's real _onBlur/_onInput are both perfectly synchronous, so a browser's input event's handler ALWAYS fully completes (any model write included) before its subsequent blur event's handler can even start — no handler-ordering question is possible there. Here, BOTH handlers are async (resolving the SAME DateAdapter factory), which gives the event loop a real opportunity to run blur's handler to completion WHILE input's own handler is still suspended on its own await — confirmed live (reproducible 100% of the time, not a timing flake — simulating a fast, essentially instantaneous type-then-blur, exactly what a real fast typist or any automated driver does): without this, _onBlur reading a not-yet-updated picker.value.value would see null and skip reformatting forever (nothing re-triggers it afterward). Re-deriving from the native text makes blur self-sufficient regardless of which handler's chunk/promise happens to settle first.

setMatDatepickerValue(picker: MatDatepickerHandle<D>, value: D | null) => void

Imperatively sets picker.value from OUTSIDE the picker's own input/calendar handlers, keeping the rendered native input's displayed text in sync — the SAME writeFormattedValue call every INTERNAL selection path (handleDatepickerUserSelect/applyDatepickerSelection/ handleDatepickerInput) already makes, just reachable by a consumer. See use-mat-datepicker.ts's UseMatDatepickerOptions.value doc comment for why this exists (a form library's reset()/setInput(), e.g. Formisch — see qwik-material/README.md's "Using with Formisch" — needs to put a date back into the picker after mount, which the hook's own value OPTION can't do: a plain hook-call argument, unlike a component$ prop, has no live tracking to hook a resync into). Call from your OWN component's useTask$/event handler, never from render (a signal write during render is the Qwik v2 pitfall this whole project's SYNC.md files warn about repeatedly).
