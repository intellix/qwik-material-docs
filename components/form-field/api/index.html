color?MatFormFieldColor | nullMirrors upstream MatFormField.color: ThemePalette = 'primary'.
Details

undefined (the common case — prop simply omitted) falls back through config.color to 'primary', same as every other config field here. null is a DIFFERENT, deliberate sentinel: "force this to resolve as literally unset," needed because Angular's own default class-field initializer ('primary') is PRESERVED only when a template never binds [color] AT ALL — a template that writes [color]="expr" UNCONDITIONALLY (even when expr evaluates to undefined) OVERWRITES that default with the literal undefined, because a property binding always assigns on every change-detection run regardless of the bound value. qwik-material/paginator's embedded page-size form field is exactly this case (paginator.html: [color]="color", where MatPaginator's own color input has no default and is unset in every parity scenario) — confirmed live, its <mat-select> panel gets mat-undefined (_parentFormField?.color read literally falsy), NOT mat-primary, unlike every OTHER select scenario's <mat-form-field> (which never binds [color] at all, so the class-field default survives untouched). JSX can't distinguish "prop omitted" from "prop bound to an undefined expression" (both are just undefined), so MatPaginator passes null explicitly for this one case — see mat-paginator.tsx. This only affects the value exposed to the embedded CONTROL via MAT_FORM_FIELD_CONTROL_STATE.color; the form field's OWN host classes below are unaffected either way (!== 'accent' && !== 'warn' is true for undefined exactly as it is for 'primary', matching upstream's OWN host-class formula, which — unlike the ternary _parentFormField?.color === 'primary' a CHILD like MatSelect reads — never distinguishes the two).

Hooks

useMatFormControl: (options: MatFormControlOptions) => MatFormControl

Qwik's replacement for new FormControl(value, validators) — see the module doc comment for the full design rationale.

Details

Validators are NOT passed here; call {@link matValidationErrors} (or {@link matControlInvalid}/ {@link matControlHasError}) with the returned control's .value wherever you need the validation result (typically right where you build the <MatFormField>/<MatInput>/<MatError> JSX for it).

useMatFormFieldProvider: (config?: MatFormFieldConfig) => void

Provides {@link MAT_FORM_FIELD_CONFIG} for this subtree — call once near the root (or anywhere deeper, to override just that part of the tree) so every MatFormField descendant resolves its defaults from config instead of {@link MAT_FORM_FIELD_CONFIG_DEFAULTS}. Only this one context is provided; every other qwik-material configuration context stays whatever an ancestor (or nothing) already provided.

resolveErrorStateSync(snapshot: MatErrorStateSnapshot, mode: 'touched' | 'dirty') => boolean

Synchronously evaluates one of the two BUILT-IN matcher modes — upstream ErrorStateMatcher/ ShowOnDirtyErrorStateMatcher's own isErrorState bodies, verbatim, just with !!(control && ...)'s null-control guard already folded into the formBound check every call site performs separately (upstream: isErrorState returns false outright for a null control — this port's formBound IS that same "is there a real bound control" condition).

Details

Deliberately NOT used for the QRL matcher case — a QRL must be resolved (.resolve() or calling it directly) before it can run, which cannot happen inside a synchronous render body (component$ cannot return a Promise in this Qwik version). Every control therefore keeps its OWN useSignal/useTask$ pair (the SAME pattern qwik-material/select/mat-select.tsx's triggerLabel and qwik-material/datepicker/mat-month-view.tsx's dateFilter/dateClass resolution already establish — see select/SYNC.md's compareWith section for the full write-up of why): a synchronous useSignal initializer calls this function directly for the correct value on the very first render, and a useTask$ (no browser-only strategy, so Qwik awaits it before finalizing SSR output) recomputes it on every relevant change — synchronously, via this same function, for the two built-in modes, or by resolving+calling the QRL for a custom one. This function itself never touches a QRL, so it needs no core/error-state- matcher.ts consumer to duplicate this formula by hand.

MatValidationErrors

A small, framework-appropriate replacement for Angular's reactive forms (FormControl + Validators), used by the error-state form-field scenario and intended to stay reusable for select/datepicker/chips later (see docs/superpowers/specs/2026-10-27-qwik-material-remaining-components-roadmap.md and form-field/SYNC.md's "key design decision").

Details

Mirrors upstream's FormControl/Validators/NgControlStatus shape closely enough to port 1:1 (value/touched/dirty, Validators.required/ .email → {@link matRequiredValidator}/{@link matEmailValidator}, hasError('key')), while staying a plain, inspectable, Qwik-native primitive. ## Why validators are never stored inside the reactive useStore() useMatFormControl()'s result is routinely passed as a prop ACROSS a component boundary — to <MatInput formControl={fc}>, and indirectly to <MatFormField> via readControlProps() introspecting the control JSX descriptor (see core/mat-form-field-control.ts). Qwik's useStore() values and QRLs ($(...)-wrapped functions) are BOTH safe to carry across that boundary (they're first-class, independently resumable); a PLAIN closure/function is not — Qwik has no general mechanism for serializing an arbitrary function reference embedded as a plain object property (as opposed to a QRL, or a named, statically-importable symbol), and even noSerialize() only keeps a value alive for the remainder of the SAME execution context (the server's render, OR the current browser tab after it was created there) — it is never a way to ship a function from server to client. So MatFormControl returned by {@link useMatFormControl} carries ONLY plain data (value/touched/dirty, all serializable primitives) and QRL methods (setValue$/markAsTouched$/markAsDirty$, natively serializable). Validators are **never** attached to it. Instead, the validator functions ({@link matRequiredValidator}, {@link matEmailValidator}) are plain, stateless, MODULE-LEVEL exported functions — like upstream's Validators.required/Validators.email — invoked DIRECTLY by the consumer (the route/page component that owns the useMatFormControl() call) via {@link matValidationErrors}, inline, in the SAME synchronous render pass that builds the JSX tree it hands to <MatFormField>/ <MatInput>. The RESULT of that call (a plain MatValidationErrors | null, or the booleans derived from it) is what crosses the component boundary — never the functions themselves. This exactly mirrors how the Angular mirror scenario itself is written (@if (nameControl.invalid) { <mat-error>...</mat-error> } — the TEMPLATE, not MatFormField, decides whether to render the error). Because the route reads fc.value/fc.touched/fc.dirty directly to compute those booleans, Qwik's normal signal-subscription reactivity means the route's OWN render re-runs whenever those fields change (e.g. after fc.markAsTouched$() from a blur handler), rebuilding fresh <MatFormField control={...} errors={...}> JSX with up-to-date values — ordinary parent-rerenders-on-prop-change reactivity, nothing exotic needed for this path (unlike the focused/empty/shouldLabelFloat trio, which has no consumer-visible owner and uses the MAT_FORM_FIELD_CONTROL_STATE context instead — see core/mat-form-field-control.ts). Mirrors Angular Forms' ValidationErrors (a map of failed validator keys to truthy detail — simplified to true here, since no scenario needs the richer per-key detail object Angular supports).
