Hooks

useMatMenuProvider: (config?: MatMenuProviderConfig) => void

Provides {@link MAT_MENU_DEFAULT_OPTIONS} and {@link MAT_MENU_SCROLL_STRATEGY} for this subtree — call once near the root (or anywhere deeper, to override just that part of the tree) so every menu created below resolves its defaults/scroll strategy from config instead of the hardcoded fallbacks. Only these two contexts are provided; every other qwik-material configuration context stays whatever an ancestor (or nothing) already provided.

createMatMenu(props: MatMenuProps) => MatMenuRef

Builds a MatMenuRef — the Qwik-port equivalent of declaring <mat-menu #menu="matMenu">…</mat-menu> and later referencing #menu via [matMenuTriggerFor].

Details

Call it as a plain function (not JSX) wherever you would declare the Angular template's <mat-menu> tag; pass the result to <MatMenuTrigger menu={…}> (top-level triggers) or <MatMenuItem menu={…}> (submenu triggers), and ALSO render <MatMenu panelClass={…} /> as a sibling of the trigger to reproduce the empty placeholder host element Angular leaves at the <mat-menu> declaration site (see mat-menu.tsx). See menu/SYNC.md for the full rationale.

getParentInnerPadding(itemEl: HTMLElement) => number

Walks up from a just-opened submenu's trigger item to its PARENT panel's first item, mirroring this._parentInnerPadding = firstItem._getHostElement().offsetTop — the vertical compensation so a submenu's first item visually aligns with its trigger instead of sitting 8px (the panel content's own top padding) too low.

MatMenu(props: MatMenuPlaceholderProps) => JSXOutput

The empty placeholder Angular leaves at a <mat-menu> declaration site.

Details

Upstream's <mat-menu> template (menu.html) is a *lone* <ng-template>: its content is only ever instantiated later, inside the overlay, by whichever trigger attaches it. But <mat-menu> is still a *component* (selector mat-menu), so Angular still creates and renders its own HOST element at the point it's declared — it just stays empty (no children) there forever. MatMenu's host bindings ([attr.aria-label]/ [attr.aria-labelledby]/[attr.aria-describedby] all hard-bound to null) exist specifically to strip the static-attribute echo a bare aria-label="…" would otherwise leave on this empty tag — irrelevant here since this component never receives those props at all (the real aria-label lives on createMatMenu()'s config, applied only to the real overlay panel by MenuPanel). The one upstream quirk THIS placeholder must reproduce: MatMenu.panelClass's setter runs this._elementRef.nativeElement.className = '' whenever a non-empty value is set — so the host renders <mat-menu class=""> (present, empty string) rather than no class attribute at all. A plain function (not component$): purely static output, no hooks needed.

MatMenuContent(props: {children?: JSXChildren}) => JSXOutput

Marks lazily-rendered menu content. Mirrors <ng-template matMenuContent> (src/material/menu/menu-content.ts's MatMenuContent, backed by a real DomPortalOutlet whose own host is a bare, attribute-less <div>). Use inside a createMatMenu({content$: $(() => <MatMenuContent>…</MatMenuContent>)}) body wherever upstream would nest <ng-template matMenuContent> — it reproduces the EXTRA wrapping <div> the real DomPortalOutlet leaves around the lazily-attached content (confirmed live: a non-lazy menu's .mat-mdc-menu-content contains its items directly, while a matMenuContent one wraps them in one extra bare <div> — see angular-parity.spec.ts's lazy-content scenario). A plain function — purely structural, no hooks needed.

openMenu(itemsJsx: JSXOutput, options: OpenMenuOptions) => Promise<void>

Opens a menu (or submenu) overlay. Mirrors MatMenuTriggerBase._openMenu: builds the position strategy + overlay config, creates the overlay, wires the keyboard/outside-click dispatchers, and (once attached) builds a FocusKeyManager over the rendered .mat-mdc-menu-item elements and optionally auto-focuses the first one.

Details

Simplifications vs. upstream (see menu/SYNC.md): items are resolved via menu.content$() by the CALLER before this is invoked (itemsJsx parameter) rather than inside the panel component, so no JSXOutput ever crosses an SSR-serialization boundary (this whole flow only ever runs client-side, after a real interaction — see menu-ref.ts's doc comment); the key manager's items are built from the LIVE rendered DOM (.mat-mdc-menu-item elements) rather than a QueryList, since nothing in this port adds/removes items while a menu is already open; panel position classes use the statically configured xPosition/yPosition rather than the position strategy's resolved connection pair (every parity scenario's preferred position always fits the viewport, so the two are always equal in practice). async so the QRL<() => ScrollStrategy> escape hatch of a configured ScrollStrategyDescriptor can be awaited (see resolveScrollStrategyDescriptor) - the common, non-QRL case resolves with no actual suspension. Both call sites (use-mat-menu-trigger.ts, mat-menu-item.tsx's openSubmenu) already call this from inside an async $(...) and now await it, so ordering against their own following statements (onMenuOpened$) is preserved.

resolveMenuConfig(menu: MatMenuRef, defaults: MatMenuDefaultOptions) => ResolvedMenuConfig
