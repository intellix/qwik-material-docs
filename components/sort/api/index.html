Components

MatSort : Component<MatSortProps>
NameTypeDescription
as?'table' | 'div'Which host tag MatSort renders. Default 'table'.
active?stringThe id of the most recently sorted column. matSortActive.
Details

LIVE — mirrors upstream's plain mutable active field: Angular's template binding ([matSortActive]="x") re-assigns this.active on every change-detection cycle where the BOUND EXPRESSION's value differs from what it last wrote, independent of whatever MatSortHeader.sort() (a click) may have separately mutated it to since. This prop follows the identical rule: <MatSort> re-applies active/direction to its internal sort state ONLY when ITS OWN prop value has changed since the last time this component last observed it — a header-driven change (toggleOnInteraction$, writing sortValue.value directly) is never clobbered by an unrelated re-render that re-passes the SAME active/ direction prop values it had before. Programmatically changing this prop does NOT emit onSortChange$ — matches upstream, where ngOnChanges() only calls _stateChanges.next() (a private change-notification Subject MatSortHeader doesn't even subscribe to for sortChange purposes), never sortChange.emit() — only sort() (called by a header's click/keydown, or directly by a consumer holding a MatSort instance) emits that. See computeNextSort()/ getNextSortDirection() (re-exported from public-api.ts) for the pure-function equivalent of calling sort(sortable) programmatically: compute the next Sort, assign it to the signal you pass as active/ direction here, AND fire your own onSortChange$-equivalent side-effect yourself (this port doesn't emit on your behalf for a props-driven change, matching upstream exactly).

Hooks

useMatSortProvider: (config?: MatSortConfig) => void

Provides {@link MAT_SORT_CONFIG} for this subtree — call once near the root (or anywhere deeper, to override just that part of the tree) so every MatSort / MatSortHeader descendant resolves its defaults from config instead of its own hardcoded fallback. Only this one context is provided; every other qwik-material configuration context stays whatever an ancestor (or nothing) already provided — see README.md's "Configuring the library" section.

useMatSortStyles: () => void

Registers this entry point's CSS — scss/sort/sort-prebuilt.scss, compiled inside @layer qwik-material — for the rendering document, once: upstream's MatSortHeader's styleUrl: 'sort-header.css' (sort-header.ts) (src/material/sort/), attached when the component is first created, unscoped (ViewEncapsulation.None). Server rendering writes it before the first instance; a component first rendered in the browser brings it with its own chunk. Call it as the component's FIRST hook — Qwik keys a useStyles$ <style> by the call site AND the hook's index in the component, so only first-hook calls share one <style> (README "Component styles"). Exported for markup rendered without the component (a hand-written host, a plain render function).

Ported from upstream's MatSort.sort(sortable) (src/material/sort/sort.ts): switching to a new column adopts its own start override (falling back to the table's start); re-activating the already-active column advances the cycle, using the column's own disableClear override (falling back to the table's resolved disableClear).

MatSortSharedState

Per-instance state shared by <MatSort> and every descendant <MatSortHeader> via MAT_SORT_STATE — split into two INDEPENDENT signals, each with a single owner, rather than one combined signal both sides read-and-rewrite:

Details

- sortValue (active/direction): SELF-owned by the table, exactly mirroring upstream's MatSort.active/.direction plain mutable fields, which MatSortHeader._toggleOnInteraction() mutates directly via this._sort.sort(this) — there is no consumer round-trip (the (matSortChange) output is fire-and-forget; nothing requires the consumer to feed the new value back into [matSortActive]/ [matSortDirection], confirmed by every parity scenario's template). <MatSort> initializes it ONCE (lazy useSignal) and never writes to it again; only <MatSortHeader>'s toggleOnInteraction$ writes sortValue.value thereafter — the most faithful port of "a child directly mutates its parent directive's own fields" is a child directly mutating a shared Signal's .value. - tableConfig (start/disableClear/disabled/onSortChange): OWNED by <MatSort>, which overwrites it with a freshly-computed object on EVERY one of its own renders (so it stays reactive to prop/config changes, matching upstream's @Input()s); <MatSortHeader> only reads it, never writes. Why split instead of one combined signal: <MatSort>'s own render needs to keep tableConfig fresh every time it renders, which means WRITING to that signal unconditionally. If active/direction lived in the SAME signal, preserving them across that write would require reading the signal's CURRENT value first ({...state.value, start: ..., ...}) — which subscribes <MatSort> to its OWN signal. Since the write produces a brand-new object (a different reference every time, even with identical field values), Qwik's signal-change detection (reference-based) would then re-schedule <MatSort> itself as a subscriber — which renders again, reads-and-rewrites again, forever: an infinite reactive loop. This was caught empirically (clicking a header froze the page; isolated via a standalone Playwright script showing page.locator(...).textContent() hanging past its 30s timeout — the main thread never yielded). Splitting the two concerns into separately-owned signals means <MatSort> never reads the signal it owns-and-rewrites (tableConfig), so writing to it cannot re-trigger <MatSort> itself — only <MatSortHeader> instances, which merely read it, re-render once and stop. See SYNC.md's "a real bug found and fixed" entry for the full narrative.
