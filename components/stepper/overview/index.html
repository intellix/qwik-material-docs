Stepper

Guides a user through a sequence of numbered steps.

OverviewAPIExamples

qwik-material's stepper provides a wizard-like workflow by dividing content into logical steps.

Material stepper builds on the foundation of the CDK stepper that is responsible for the logic that drives a stepped workflow. MatStepper extends the CDK stepper and has Material Design styling.

Stepper buttons

Upstream has two directives to support navigation between steps: matStepperPrevious and matStepperNext. qwik-material exposes the same behavior via useMatStepperNext()/ useMatStepperPrevious() hooks (see Angular → Qwik notes below), spread onto whatever button component you use.

Linear stepper

The linear prop can be set on <MatStepper> to create a linear stepper that requires the user to complete previous steps before proceeding to following steps. For each step, the stepControl field can be set on its MatStepDef to a plain {valid, invalid} snapshot used to check the validity of the step (see Angular → Qwik notes).

Alternatively, if you don't want to use form validity, you can pass the completed field on each step's MatStepDef, which won't allow the user to continue until it becomes true. Note that if both completed and stepControl are set, stepControl takes precedence.

Completed step

By default, a step's completed field returns true if the step is valid (in case of a linear stepper) and the user has interacted with the step. You can also override this default completed behavior by setting the completed field as needed.

Overriding icons

Upstream lets you override the number/edit/done/error (or any custom state string) step-header icons by placing a matStepperIcon template for each icon you want to override. qwik-material exposes the same behavior via <MatStepper>'s stepperIcon prop — a Partial<Record<StepState, JSXOutput>> keyed by the icon state it replaces. Content provided for a state completely replaces the default icon markup for every step currently resolved to that state (see Angular → Qwik notes for the one difference from upstream).

Step States

You can set the state of a step to whatever you want via its MatStepDef.state field. The given state by default maps to an icon, same as upstream.

Error State

If you want to show an error when the user moved past a step that hasn't been filled out correctly, you can set the error message through the step's errorMessage field and configure the stepper to show errors via the showError option on useMatStepperProvider()'s global options (mirrors upstream's STEPPER_GLOBAL_OPTIONS/showError). Note that since linear steppers prevent a user from advancing past an invalid step to begin with, this setting will not affect steppers marked linear.

Lazy rendering

By default, the stepper renders all of its content (the content field on each step's MatStepDef) when it's initialized, and keeps it rendered. For content that should only render once a step is first selected — and then stay rendered, exactly like eager content, never detached again — set a step's lazyContent field instead of (or alongside) content. This mirrors upstream's matStepContent template.

Accessibility

The stepper is treated as a tabbed view for accessibility purposes, so it is given role="tablist" by default. The header of a step that can be clicked to select the step is given role="tab".

Angular → Qwik notes

  • Steps are a data array (steps: MatStepDef[]), not <MatStep> children. Same "content projection Qwik can't introspect" reasoning as MatTabGroup's tabs array — see the Tabs overview's Angular → Qwik notes for the full write-up. MatStepDef mirrors CdkStep's inputs 1:1 (label/labelTemplate/stepControl/editable/optional/ completed/hasError/state/errorMessage).
  • Stepper navigation buttons are a hooks pattern, not stackable directives. Upstream's matStepperNext/matStepperPrevious attach to any existing button; useMatStepperNext()/ useMatStepperPrevious() return the equivalent hostProps, spread onto whatever component you're using as the button. Each hook call must happen in a component rendered INSIDE the owning <MatStepper>'s active step content (context resolves by the actual render tree).
  • Step-icon overrides (stepperIcon) are static content, not a per-occurrence template. Upstream passes each override a fresh {index, active, optional} context per step that reaches that state (any number of steps can share one override); Qwik can't synchronously re-invoke a per-occurrence render callback inside the stepper's own render (the same reasoning that rules out a per-row cell-render callback for <MatTable>), so an override here is a single static JSXOutput shared by every step currently in that state. Sufficient for every known use — material.angular.dev's own icon-override example never references the context either.
  • Step content is never detached once rendered, regardless of lazy/eager origin upstream. Unlike MatTabGroup (which detaches off-screen tab content by default), neither content nor lazyContent is ever detached once rendered here — lazyContent only controls the FIRST render timing (deferred until the step is first selected), not ongoing attach/detach.
  • No MatStepperIntl localization yet. Step-header strings (e.g. "Optional") are hardcoded English; no DI-style override mechanism is ported.
  • Dynamic orientation switching based on viewport isn't demonstrated as a live example yet — orientation itself is a plain reactive prop (just assign a signal driven by your own media-query listener), the gap is only in having a ready-made example.
